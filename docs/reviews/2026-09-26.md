## The two owner Dev Notes — one is a shipped bug I root-caused, one still stands

### 1. [HIGH — client bug, Dev Note] Warding Wall does not cast → WALL-CAST-FIX (root cause found)

*"Aegis's Warding Wall does not cast successfully."* **This is a bug WALL-ROTATE introduced, and I found
the exact line.** WALL-ROTATE made a wall's aim require **both** halves — the engine's `aimIsLegal` for
`'wall'` now ends `... && isAimStep(aimStep)` (`resolve.ts`), refusing any wall order with no step. On the
client, `aimFor` correctly puts the rotation into `draft.aimStep`, and a new `isPlacedRotatable` (=wall)
drives the rotate-row UI. **But `toUnitOrders` still gates the aimStep carry on the *old* predicate:**

```
if (isRotatable(ability) && isAimStep(draft.aimStep)) order.ability.aimStep = draft.aimStep;
```

`isRotatable` is `line || cone` (`targeting.ts:176`) — it does **not** include `wall`. A wall is
`isPlacedRotatable` but **not** `isRotatable`, so **the rotation is dropped when the order is built**, the
engine receives a stepless wall order, and `aimIsLegal` refuses it. The wall never casts. The **preview**
uses `aimFor` directly (with the default rotation), so it looks perfect on screen — which is exactly why
this shipped green. **Fix: backlog WALL-CAST-FIX (client, HIGH)** — carry `aimStep` for a placed-rotatable
shape too (gate on `isRotatable(ability) || isPlacedRotatable(ability)`, or simply on
`isAimStep(draft.aimStep)`), and ship the **order-build/resolve** regression the preview-only test never
had. **No engine change** — the engine is correct; the client drops the field.

**Why the whole suite missed it:** *no client test drives lock-in → submit → resolve for `warding_wall`*
— it is only ever preview-tested (`warding-wall-preview.test.ts` stops at the aim highlight;
`harness-flows.test.ts` drives only Vex's line/square/free). The engine's own wall tests pass because they
construct the order with `aimStep: WALL_FACING` **directly** (`warding-wall.test.ts:320`), bypassing the
client `toUnitOrders` that drops it. Textbook "pure function passes, real order-build broken."

### 2. [MED — client, Dev Note] Ram Charge doesn't read as a line attack → RAM-LINE-PREVIEW-FIX (still stands)

*"Bastion's Ram Charge is still not a linear dash/attack preview."* Unchanged by session 9. The engine is
correct (`chargeHits:"all"`), and the preview draws the route tiles + a landing marker, **but nothing
marks the crossed enemies as hit and no damage number appears along the line** — `ram_charge` has no
`impact` field, so `impactPreview`'s discs are empty and there is **no client mirror of the engine's
`walkCharge`/`chargeHits` derivation**. A real `line` attack lights its whole tile run (`lineSquares`) and
`previewNumbers` stamps every enemy on it; a `path` charge never reaches that path. **Fix: backlog
RAM-LINE-PREVIEW-FIX (client)** — enumerate the straight charge path, mark every crossed enemy with its 15
(reuse the line-attack tell; read the engine's derivation, don't recompute), plus the existing landing
marker. Preview-only.
