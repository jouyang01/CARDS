## Issues, ranked

### 1. [HIGH — blocks playtest] An aimed action can't be committed; it keeps following the mouse
**Addresses Dev Note: "Right now, the attack, dash and prep actions cannot be locked in. As I am
moving my mouse around the board, the attack action follows my mouse around. I need to be able to
lock in the action when I click the tile on the board so the action stops following the mouse."**

Root cause (`packages/client/src/app.ts`): `onBoardClick` commits the aim to the draft
(`draft.aim = aim`) but **never disarms the mode** — `mode` stays `'aim'`. So the next
`mousemove` fires `onBoardHover`, which re-sets `hover.square`, and `previewAim`
(`if (ability && mode === 'aim' && hover.square !== undefined) return aimFor(hover.square)`)
keeps rendering the mouse-following aim *over* the committed one. The commit is stored but
visually and functionally overridden by the continuing hover-follow, so the player perceives it
as never locking in. The `mode === 'move'` branch has the same defect.

**Fix (backlog UI1-fix):** on a committing board click, set `mode = 'idle'` and `clearHover()`
(both the `aim` and `move` branches), so `previewAim` falls through to the committed `draft.aim`
and `onBoardHover` early-returns (mode idle) — the action stops following the mouse and the
committed aim is what shows. Re-aim by re-selecting the ability (UI1's "replace by choosing
another ability"). Ships with a client test: after a board click in aim mode, a subsequent
`onBoardHover` does not change the rendered aim. Small, localized.
