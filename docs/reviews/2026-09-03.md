## Done well (one line)

The server put its rules in plain modules behind a `Sink` interface and left the Durable Object a
forwarder — so "a socket is not a seat" and "join-past-bound is rejected" are tested with fake
sockets in plain Vitest, and the day the DO grows logic is the signal to move it *out*, not to add
a runtime. That is the right call for code that has to be provably correct before it can ever be
deployed.

## M3-PROTOCOL — the two rulings it was blocked on (Builder OQ #4)

Folded into the backlog item's Spec Notes so it is unblocked:

- **Where the control map lives.** `Seat` gains `unitIds: string[]` (the DO owns it, ARCHITECTURE
  §45). **Interim until M3-LOBBY exists:** assign characters to seats **on match start** (once the
  seats are full and start is triggered) with a **deterministic deal** — reuse the client's
  `dealTeams`/`createMatch` seating so client and server agree. M3-LOBBY later replaces the fixed
  deal with each player's picks; M3-PROTOCOL should not block on the lobby.
- **`mergeSeatOrders` moves into the engine.** The server may not import the client, and the merge
  is **pure order-shaping** (no DOM/IO) — so it belongs in `packages/engine` as a shared order
  utility (e.g. `orders.ts`), imported by **both** client and server. This is exactly the "shared
  verbatim by client and server" model (ARCHITECTURE §19); widening the engine surface with a pure
  helper is correct, not a leak.
