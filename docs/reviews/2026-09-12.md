## Issues, ranked

### 1. [HIGH — client, owner-directed, repeat] WAYPOINTS doesn't work for the player (Dev Note #1)

*"WAYPOINTS is not working. I cannot hold shift + click to move to a waypoint."* Root-caused — the
feature is wired and unit-tested but the interaction is wrong for how a player uses it:
- `appendWaypoint` (`targeting.ts:518`) accepts **one adjacent step per click** and **silently
  refuses** anything else (refusal is a bare `undefined`, no tell).
- the Shift-click branch runs **only while move mode is already armed** (`app.ts:1377,1382`) — a
  freshly-selected unit with no armed Move does nothing on Shift-click.

So the natural gesture — select a unit, Shift-click a tile a few squares away to "move to a
waypoint" — produces nothing (non-adjacent → refused, or move never armed), with no feedback either
way. **My own v1 ruling ("non-adjacent is refused, keeping tile-by-tile literal") is the cause and I
reverse it.** **Fix: backlog WAYPOINTS-FIX (client, HIGH)** — a Shift-click drops a waypoint at **any
reachable tile** and the client **routes the segment** to it (`pathTo`, obstacle-aware, MOVE-FOG
filtered), appending it; **Shift-click auto-arms move** when a movable unit is selected and nothing is
mid-aim; an unroutable click shows the **AIM-RANGE-TELL marker**, never silence; the budget readout
draws down per segment. Adjacent clicks stay one-step segments, so exact tile-by-tile control
survives. Ruled in edge-cases (WAYPOINTS-FIX). No engine change.

### 2. [MED — client, large] The networked match isn't rendered yet (Dev Note #2 / OQ #1)

M3-LOBBY-UI shipped the pick screen, socket wiring, `?room=CODE` boot, and a `lobbyReady`-gated start
— but **on match start the page says "not built" instead of rendering a networked board.** `app.ts`
still merges seat orders and calls `resolveTurn` itself (hot-seat); a server-authoritative match needs
the lock-in to become a `submit`, fog from `visibleSquares` instead of the local `fogView`, and the
hot-seat handover gone — a controller rewrite in a 1750-line file with the render e2e downstream.
**Fix: backlog M3-NET-BOARD (client, large)** — the spine of "continue the lobby." The Builder
correctly stopped at a clean seam.

### 3. [MED — client] No way to create a room from the UI; map/format live at creation (OQ #5, #6)

`?room=CODE` works but nothing calls `POST /rooms` — a player needs a link someone made with `curl`.
And map/format are room-level (the DO fixes them), so the M3-LOBBY-UI AC's "each seat picks map +
format" was wrong. **Ruled: MAP/FORMAT are room-level (host's choice at creation), not per-seat.**
**Fix: backlog M3-ROOM-CREATE (client)** — a "Create room" button that `POST`s with the host's
map/format choice, gets a code, and redirects to `?room=CODE`. This is "the last thing between the
lobby and somebody actually playing over the network."
