## Done well (one line)

M3-HIDDEN filters by *removal* and routes every visibility question back to the engine's own
queries — so the networked hidden-info boundary can never quietly diverge from the vision the rest
of the game already computes, and a blanked-vs-absent choice that would have leaked the *count* of
hidden enemies was caught and made right.

## Issues, ranked

No correctness or determinism defects. The items below are OQ resolutions, the owner's UI batch to

### 1. [MED — interim leak, closes at M3-DEPLOY] The `POST /rooms/:code/start` route is unauthenticated (Builder OQ #5)
M3-START's short-room start is a public HTTP route (no client socket layer exists until M3-LOBBY),
so anyone with a room code can start that room. **Fine for a dev build, not for deploy.** **Ruled:**
M3-LOBBY **deletes** the route when its start button lands; if it outlives the lobby, **M3-DEPLOY
must gate/remove it**. Recorded in both items' ACs. No action now.

### 2. [MED — owner directive → backlog] The damage preview must account for Might + Cover + Weakness (Dev Note #1)
PREVIEW-NUMBERS (and the decoy/nameplate previews) show the **nominal** amount. The owner wants the
number the hit would **actually deal**: apply the attacker's current **Might/Weaken** and **cover**
through the engine's own `computeDamage`/`isBehindCover`. **Fix: backlog PREVIEW-MODIFIERS** (client
+ export the two pure helpers if not already exported). Plan-time honesty: a this-turn Adrenaline
(Might applied at Blast start, after lock) can't be known, so the preview reflects *current* state —
correct. Ruled in edge-cases.

### 3. [LOW — reachable-but-guarded] Enemy seat ids appear in the pre-reveal Decision payload (Builder OQ #4)
The Decision payload names *which* seats have locked in, enemies included — no plan leaks, but a
seat id is the one identity that needn't appear pre-reveal. **Ruled:** own-team lock state stays
per-seat (UI-INTENT needs it); the **enemy team's readiness becomes a bare locked-count**. **Fix:
backlog M3-LOCKLIST** (small) — change it now, before M3-LOBBY builds a waiting UI on the richer
shape (the Builder asked to settle it early). Ruled in edge-cases.

### 4. [LOW — carried coverage gap, better technique found] The camo red tile e2e (Builder OQ #1)
The Builder closed CAMO-E2E-FINISH as unit-covered-only and showed the AC's `pixelAt` technique
can't work (no board-square→screen-pixel map in the e2e). **Their proposed route is better and needs
no hook:** `findPixels(before, isBrushGreen)` → drive the seeded unit to attack → assert those same
coordinates now match `isCamoRed` (a before/after delta at fixed coords dodges both the projection
and the counting problem). **Fix: backlog CAMO-E2E-FINISH** re-specced to that technique — but it's
a real browser drive (a unit must attack from inside brush), not "small." Low priority; the *rule*
stays covered by `camo-reveal.test.ts`.

### 5. [LOW — Designer, routed] Pad squares are placeholders re-laid to satisfy PADS-SPREAD (Builder OQ #2)
The Builder re-laid both maps' pads as mirrored singles to pass the new adjacency rule — they
satisfy the rule and the mirror guard "and nothing else" (`duel-arena` now stacks all six in the two
central columns). **Route to Designer** for real placement (lanes, sightlines, which pad is worth
contesting). Timings untouched.
